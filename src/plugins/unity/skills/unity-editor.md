# Building this Unity game in its editor

This game is built in the user's open Unity editor through unity-editor__list_commands, unity-editor__describe_command and unity-editor__run_command (Unity's Pipeline package, com.unity.pipeline). list_commands names every command the open editor offers, what each does and its tags; describe_command lists one command's parameters; run_command runs it with those parameters. A command's name is a group and a name, such as scene save or editor.playmode stop, and this page uses those; a project still on an older Pipeline package lists one word instead (save_scene, editor_stop, run_script, capture_game_view), and Genex moves a project it set up to the current package the next time it opens it. Always call a command by the exact name list_commands gives, and name its parameters as describe_command spells them (dry-run and output-path on the current package). Read a command's parameters before you first run it: a wrong or missing one fails with the editor's own words for what it wants. Calls go to this game's own Unity project (the folder holding ProjectSettings/, in the game's folder) and only while it is open in Unity with the Pipeline package. When a call says the project is not open, call unity__open-editor; when it says the project has no Pipeline package, call unity__setup (the user confirms it); when Unity is busy or still starting, call again in a moment; when it says Unity's main thread ran nothing, wait a minute and call again, and only if that keeps happening call unity__restart-editor (the user confirms it; Genex saves first while Unity still answers, else unsaved editor work is lost). To close Unity, call unity__quit-editor: it saves first; open it again with unity__open-editor. Anything else a call says to do, tell the user instead of retrying.

Scripts are C# files under Assets/: write and edit them as files. After a script changes, call script recompile and read script recompile_status until it is idle: its errors are the compile errors to fix, and while Unity reloads its scripts its commands wait or answer that it is busy, which is not a failure. A new script's type exists only after that recompile. Keep every .meta file beside its asset: Unity writes them, and they hold the ids scenes and prefabs point at, so never write one by hand, and move, rename or delete an asset with the editor's asset commands, which carry the .meta along. Scenes (.unity) and prefabs are files Unity owns: change them with editor commands, not by editing their text. Library/, Temp/, Logs/, obj/ and UserSettings/ are Unity's scratch: never edit them.

Build the game into its scenes, not at runtime: the level, its lights and its camera belong in the saved scene, where the user sees and edits them in Unity and where Genex's save points and reviewer see them, since their pictures are the main camera's view of the saved scene outside Play mode (a scene that builds itself only when Play starts gives them an empty frame). Keep the main camera where the player first sees the game. Build with code, not one command at a time: for a level, a layout or anything with many objects, write a C# file with a static method under Assets/Editor/ (it uses UnityEditor and UnityEngine as an editor script does) and run it with run_command script run (the file and its method, as describe_command names them), which compiles that file and runs the method at once, with no recompile; keep the file, so the scene can be built again, make the method replace what it made before, then save the scene. Meshes, textures and materials such a script makes in code are saved as assets first (AssetDatabase.CreateAsset under Assets/), or the saved scene loses them. When such a script makes an asset again from a new source (a new model's meshes, say), save it under a new name and point what uses it there: copying new data over an asset Unity already loaded (EditorUtility.CopySerialized) can leave the open editor drawing the old one until Unity restarts. When a picture of the game disagrees with what the files say, the picture is what the player sees: find out why before you say the work is done. Make at runtime only what appears during play, such as spawned pucks, projectiles and effects. job batch runs several commands as one undo step.

Every change lands in the user's editor at once. Many commands that change or delete something want confirm: true, and take dry-run: true to show what they would do first. Stop Play mode (editor.playmode stop) before you edit a scene, since changes made during play are lost when it stops. Save before you say the work is done, with scene save and the scene's path, or editor save_all: only saved files are in the game's checkpoints. scene save writes a scene to the file it already has, so a scene that has no file yet can't be saved that way, and the connector refuses the save: make new scenes with scene create and a path (Scenes/Level2.unity), which gives them their file from the start, and to keep an untitled scene that already holds work, run an Assets/Editor script whose method calls EditorSceneManager.SaveScene(SceneManager.GetActiveScene(), "Assets/Scenes/Main.unity"). Never run anything that makes Unity show a dialog nobody is there to answer. To see the game, call capture game_view: the picture comes back as an image you can look at. It needs an open Game view window, or source: "camera" to render a camera; pass output-path only to keep the file, somewhere in the Unity project outside Assets/ (Captures/shot.png), so Unity does not import it as a texture. The game keeps running while Unity is behind other windows. Read the editor's log with console get.

You may do in the editor what a person does there. Add a package the game needs yourself, such as the High Definition Render Pipeline (com.unity.render-pipelines.high-definition) or the Input System (com.unity.inputsystem): package search finds it, package add takes a registry name, a repository's URL, or file: and a folder inside this game, and you read package status until it is done; scripts reload afterwards. Add a registry package by its name with no version, so Unity picks the one made for this editor: an older version may not compile on a newer Unity (the Input System before 1.20 does not on Unity 6.6), and a project with compile errors opens on a Safe Mode dialog nobody is there to answer. Genex plays the game for you and for its reviewer through the Input System, so read the game's input from that package (Active Input Handling set to Input System Package or Both), not from the legacy Input class alone. Switch the build target with build.target switch, and build a player with build run, naming its output path under Builds/ in the Unity project (confirm: true; read build status until it is completed, and call the build done only when its result is Succeeded and the files are there: a build started while scripts still compile completes with no result and writes nothing). Frame rates measured in Play mode inside the editor include the editor's own work: say which you measured. Run a menu item with editor invoke_menu and its path, but prefer a command, since a menu item that opens a dialog stops the editor until someone answers it. Not available to agents, alone or inside a batch: running C# text that is in no file (script eval), quitting Unity (call unity__quit-editor) or opening another project in it, and Pipeline's authoring root and runtime settings. A file a command names must be inside this game's folder; paths are relative to the Unity project (Assets/…).

A web build is the WebGL target (build.target switch, then build run into web/ at the game's root when Genex publishes it, else under Builds/). Set its player settings from an Assets/Editor script before you build. Genex hosting serves no compressed files, so turn compression off (PlayerSettings.WebGL.compressionFormat = WebGLCompressionFormat.Disabled). On Unity 6.6 (6000.6) and newer, WebGPU is a supported graphics API for the web, off until asked for: when the game gains from it (compute shaders, GPU-driven rendering, many lights or instances), list it above WebGL 2 with PlayerSettings.SetUseDefaultGraphicsAPIs(BuildTarget.WebGL, false) and PlayerSettings.SetGraphicsAPIs(BuildTarget.WebGL, new[] { GraphicsDeviceType.WebGPU, GraphicsDeviceType.OpenGLES3 }). Always keep OpenGLES3 in that list: the one build then runs on WebGPU where the browser has it and falls back to WebGL 2 where it does not, so nothing the game needs to be playable may depend on WebGPU alone. WebGPU needs a page served over https or from localhost; anywhere else the same build runs on WebGL 2. Before Unity 6.6 WebGPU is experimental: leave the default there.
